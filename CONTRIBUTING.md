# Contributing

Спасибо за интерес к проекту. Документ описывает, как предложить
изменение так, чтобы оно прошло ревью без лишних кругов.

## Что можно предложить

- **Баг-репорты.** Открывайте issue, прикладывайте шаги
  воспроизведения и вывод команд из `docs/TROUBLESHOOTING.md`.
- **Запросы фич.** Issue с описанием задачи и предполагаемого
  поведения. Сначала обсудим, потом PR.
- **Pull requests.** Форк → ветка → PR в `main`. Мелкие правки
  (опечатки, документация) можно сразу PR.
- **Документация.** Правки README и `docs/` приветствуются.

## Чего не стоит делать

- **Крупные рефакторинги без обсуждения.** Откройте issue сначала.
- **Добавление зависимостей.** Каждая новая зависимость — это +N МБ
  на слабой машине. Обсудите в issue.
- **Изменение схемы БД** без миграции. Сейчас схема не
  версионируется — обсудим подход.
- **Добавление JS-фреймворка.** Проект принципиально без сборки.

## Процесс PR

1. **Форк и клонирование:**

       git clone git@github.com:<your-username>/mini-llm-ui.git
       cd mini-llm-ui
       git remote add upstream https://github.com/USER/mini-llm-ui.git

2. **Ветка от свежего main:**

       git fetch upstream
       git checkout -b feat/my-feature upstream/main

3. **Окружение:**

       make install-dev
       make assets

4. **Правки.** Соблюдайте стиль (`docs/DEVELOPMENT.md`, секция
   «Стиль кода»).

5. **Перед коммитом:**

       make check

   Все три шага должны быть зелёными.

6. **Коммиты.** Conventional Commits (`docs/DEVELOPMENT.md`, секция
   «Соглашения о коммитах»).

7. **Push и PR:**

       git push -u origin feat/my-feature

   Откройте PR в `main`. Заполните шаблон. CI прогонит линтеры,
   типы, тесты, сборку и security scan.

8. **Ревью.** Мейнтейнер прочитает, оставит комментарии. Адресуйте
   их новыми коммитами (не `--amend`, не `--force-push`).

9. **Мерж.** После апрува — squash-merge. Ветку удалят автоматически.

## Что проверяет CI

Workflow `.github/workflows/ci.yml`:

- **lint** — `ruff check`, `ruff format --check`;
- **typecheck** — `mypy --no-incremental --strict`;
- **test** — pytest на Python 3.10, 3.11, 3.12, Ubuntu + один
  прогон на macOS;
- **build** — сборка wheel + sdist, smoke-импорт в чистом venv;
- **security** — `pip-audit` (CVE в зависимостях), `bandit`
  (опасные конструкции в коде).

Если CI упал — не переоткрывайте PR, добавьте фикс-коммит. CI
перезапустится автоматически.

## Стиль сообщений о баге

Хороший баг-репорт содержит:

- **Окружение:** ОС, версия Python, версия mini-llm-ui, версия
  Ollama, какая модель загружена.
- **Шаги воспроизведения.** По одному действию на строку.
- **Ожидаемое поведение.**
- **Фактическое поведение.** Со скриншотом или копией лога.
- **Логи.** `tail -50 /tmp/app.log`, если запускали отсоединённо,
  или вывод из терминала.

Шаблон подставится автоматически при создании issue.

## Стиль PR-описания

Шаблон `.github/PULL_REQUEST_TEMPLATE.md` подставится автоматически.
Заполните:

- что меняется (одно-два предложения);
- тип изменения (bug/feature/docs/refactor);
- как проверялось;
- затронутая область.

Приложите скриншот для UI-изменений.

## Что мейнтейнер ожидает увидеть

- **Один PR — одна задача.** Не смешивайте рефакторинг с фичей.
- **Тесты.** Если меняется поведение — новый тест или обновлённый
  существующий.
- **CHANGELOG.md.** Если изменение видно пользователю — запись в
  раздел `Unreleased` или текущей версии.
- **Документация.** Если меняется публичный API или поведение — 
  правка в `docs/`.

## Как сообщить о security issue

Не открывайте публичный issue. Отправьте email мейнтейнеру
(указан в `pyproject.toml` в разделе `authors`) с:

- описанием уязвимости;
- шагами воспроизведения;
- версией проекта;
- вашей оценкой severity.

Ответим в течение 72 часов. Если уязвимость подтвердится —
подготовим фикс и выпустим патч-релиз, публично раскроем после
выхода фикса. В титлах будет указано ваше имя (или псевдоним,
если предпочитаете).

## Лицензия вклада

Отправляя PR, вы соглашаетесь с тем, что ваш вклад распространяется
под той же лицензией MIT, что и проект. См. `LICENSE`.

## Вопросы

Если что-то непонятно — открывайте issue с тегом `question`.
Не стесняйтесь, лучше спросить до PR, чем переделывать.
