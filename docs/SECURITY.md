# Безопасность

Документ описывает модель угроз, принятые меры и сознательные
ограничения. Если нашли уязвимость — открывайте issue с тегом
`security` либо пишите мейнтейнеру приватно (см. `CONTRIBUTING.md`).

## Модель угроз

Приложение **локальное**. Слушает только `127.0.0.1`, не
предназначено для сетевого доступа. Аутентификации нет.

Что защищаем:

1. **Пользователя** — от XSS через ответы модели или загруженные файлы.
2. **Данные чатов** — от кражи через CSRF или DNS rebinding.
3. **Процесс** — от DoS через переполнение памяти или диска.
4. **Файловую систему** — от path traversal через имя вложения.

Что НЕ защищаем:

- **Других пользователей машины.** Любой локальный процесс/пользователь
  видит `data/chat.db` (права стандартные). Многопользовательский
  сценарий не входит в дизайн.
- **Сетевого злоумышленника.** Если открыть приложение на 0.0.0.0,
  защита становится минимальной. Не делайте так.
- **Вредоносной модели.** Ollama доверяется как источник текста, но
  её выводы проходят через `escape=True` и воспринимаются как
  недоверенные.

## Список мер

### XSS через ответы модели и вложения

**Угроза.** Модель под влиянием prompt injection из загруженного
файла выдаёт `<script>...</script>` или `<img onerror=...>`. Если
HTML проходит на страницу без экранирования — XSS в контексте
`http://127.0.0.1:5000`.

**Мера.** `mistune.create_markdown(escape=True, ...)`. Любой сырой
HTML в Markdown-строке экранируется в HTML-entities. JS-выполнение
невозможно.

**Реализация.** `mini_llm_ui/services/markdown_service.py`.

**Что пользователь может увидеть.** `<script>` как видимый текст
`<script>`, а не как исполняемый тег.

### CSRF

**Угроза.** Вредоносная страница в интернете отправляет POST на
`http://127.0.0.1:5000/chat/1/delete` от имени пользователя.
Same-Origin Policy не блокирует отправку формы.

**Мера.** Токен в сессии + проверка через `secrets.compare_digest`
на каждом небезопасном методе (POST/PUT/PATCH/DELETE). Токен
передаётся двумя путями:

- hidden-поле `_csrf` в обычных формах;
- заголовок `X-CSRFToken` — HTMX подставляет автоматически через
  `htmx:configRequest`.

**Реализация.** `mini_llm_ui/security.py`, функции
`get_or_create_csrf_token` и `enforce_csrf_protection`.

**Сознательное решение.** Отключается флагом
`CSRF_ENABLED = False` в тестах — чтобы не гонять токен через
каждый POST в 30 тестах. В продакшене всегда включён.

### DNS rebinding

**Угроза.** Злоумышленник регистрирует домен `evil.com`, настраивает
его DNS отвечать `127.0.0.1`, и жертва открывает
`http://evil.com:5000`. Браузер считает, что это тот же origin, и
разрешает запросы к localhost от имени пользователя.

**Мера.** Проверка заголовка `Host` против allow-list на каждом
запросе (before_request). Допустимы только:

- `127.0.0.1` (с портом или без);
- `localhost` (с портом или без);
- `[::1]` (IPv6 в скобках).

Fail-closed: пустой `Host` отклоняется. IPv6 без скобок (`::1`)
отклоняется, потому что RFC 7230 требует скобки.

**Реализация.** `is_allowed_host` в `security.py`. Полностью
покрыта тестами `tests/test_host_check.py` (16 параметров).

### SQL injection

**Угроза.** Классика. Через `content` сообщения, имя вложения или
`chat_id` из URL.

**Мера.** Все запросы — с placeholder-ами `?`. Никакой конкатенации
SQL-строк. `chat_id` дополнительно типизирован как `int` в маршрутах
(`/chat/<int:chat_id>`), так что Flask отбросит нечисловые значения
до вызова обработчика.

**Реализация.** `mini_llm_ui/models.py` — везде `connection.execute(
'... WHERE id = ?', (value,))`.

### Path traversal

**Угроза.** Загружаемый файл `../../../etc/passwd`. Если сохранить
его «как есть» под именем из запроса — можно перезаписать что угодно.

**Мера.** Файлы **не сохраняются на диск** вообще. Содержимое
читается в память и уходит в БД (таблица `attachments`). Имя файла
сохраняется как строка в поле `filename` — используется только для
отображения. `Content-Disposition` в экспорте формируется из
`message_id` (int), а не из пользовательских данных.

**Реализация.** `mini_llm_ui/services/file_service.py` — читает
через `uploaded_file.read()`, диска не касается.

### XSS через имя вложения

**Угроза.** `filename = "<script>alert(1)</script>.md"`. Если имя
подставляется в HTML без экранирования — XSS.

**Мера.** Jinja2 экранирует по умолчанию. Единственные места с
`|safe` — вывод `html_content` (уже прошёл через escape=True) и
`msg.role` (жёстко ограничен CHECK-констрейнтом).

**Реализация.** `templates/partials/attachment_chip.html` —
`{{ attachment['filename'] }}` без `|safe`.

### DoS через большие файлы

**Угроза.** Загрузить файл в 100 МБ → БД распухнет, память кончится.

**Мера.** Три лимита:

- `MAX_FILE_SIZE_BYTES = 256 КБ` — на одно вложение;
- `MAX_ATTACHMENT_TOTAL_SIZE_BYTES = 100 КБ` — суммарно на чат;
- `MAX_REQUEST_SIZE_BYTES = 4 МБ` — на весь HTTP-запрос (Flask).

Валидация размера — через чтение на 1 байт больше лимита (чтобы
отличить «ровно лимит» от «сверх»).

**Реализация.** `file_service.read_text_file`, `file_routes.upload`.

### DoS через много параллельных стримов

**Угроза.** Отправить 10 запросов одновременно → 10 потоков стримов
→ OOM.

**Мера.** Атомарная резервация слота. На один `chat_id` может быть
активен только один стрим. Второй POST получает 409 Conflict.
Резервация через `try_reserve` под `self._lock` — не check-then-act,
а атомарная операция.

**Реализация.** `StreamManager.try_reserve`, пре-чек
`has_active_stream` в `chat_routes.send_message`.

### Раскрытие SECRET_KEY

**Угроза.** `SECRET_KEY` в git, в логах, в world-readable файле.
Кража → подделка сессий → CSRF-токены становятся недействительны.

**Мера.** Приоритет:

1. env `SECRET_KEY` — если задан в systemd или оболочке;
2. файл `data/secret_key` — создаётся с `O_CREAT|O_EXCL, 0o600`
   (без окна world-readable);
3. генерация при первом старте.

Запись завершается `os.fsync`, чтобы power loss не оставил пустой
файл. В git `.env` и `data/` в `.gitignore`.

**Реализация.** `mini_llm_ui/app.py`, `_load_or_create_secret_key`.

### Утечка секретов в логи

**Угроза.** `logger.info(f'secret: {secret}')`.

**Мера.** В коде нет логирования секретов. Проверено вручную и
через `bandit` в CI.

### Supply chain

**Угроза.** Скомпрометированный минорный релиз зависимости приходит
на машину через pip.

**Мера на текущий момент.**

- Версии зависимостей зафиксированы в `pyproject.toml` с
  диапазонами (`Flask>=3.0,<4`), не прибиты гвоздями.
- `pip-audit` в CI проверяет известные CVE на каждом push.
- `bandit` в CI ловит подозрительные конструкции в коде.

**Что можно улучшить.** Сгенерировать `requirements.lock` с хешами
через `pip-compile --generate-hashes` и ставить с
`--require-hashes`. Пока не сделано, потому что lock-файл нужно
пересобирать вручную при каждом обновлении.

### HTMX из CDN

**Угроза.** Если `unpkg.com` скомпрометирован или DNS подменён,
браузер получит вредоносный JS.

**Текущее состояние.** `scripts/fetch_assets.sh` скачивает
`htmx.min.js` с `unpkg.com` при установке. Файл сохраняется
локально (`mini_llm_ui/static/htmx.min.js`), в `.gitignore`, в
репозиторий не коммитится.

**Что можно улучшить.**

- Добавить проверку SHA256 скачанного файла в `fetch_assets.sh`.
- Или вендорить HTMX в репозиторий (лицензия MIT позволяет).
- Или подключить через `<script integrity="sha384-...">` при
  загрузке с CDN напрямую.

### Отсутствие HTTP security headers

**Угроза.** Clickjacking (iframe), MIME-sniffing, referrer leakage.

**Мера на текущий момент.** Не реализовано. В базовой версии только
CSRF и XSS-экранирование. Headers вроде `X-Frame-Options`,
`Content-Security-Policy`, `X-Content-Type-Options` — на бэклоге.

**Почему это не критично для локального сценария.** Приложение не
предназначено для iframe-встраивания, MIME-sniffing ограничен
localhost. Для локального single-user это приемлемо.

## Что делает пользователь для своей безопасности

1. **Не выставляйте приложение в сеть.** Слушает `127.0.0.1`, так и
   оставьте. Если очень нужно — reverse-proxy с TLS и HTTP Basic
   Auth, но это вне дизайна.
2. **Задайте `SECRET_KEY` явно** на многопользовательских машинах,
   чтобы файл `data/secret_key` не читался другими пользователями.
3. **Проверяйте вложения.** Хотя HTML экранируется, содержимое
   файла уходит в модель — не загружайте секреты в чужую модель.
4. **Ограничьте права на `data/`** при необходимости:

       chmod 700 data
       chmod 600 data/chat.db

5. **Обновляйтесь.** Подписывайтесь на GitHub Release репозитория —
   security-фиксы выходят отдельными тегами.

## Что делать при обнаружении уязвимости

Открывайте issue с тегом `security` или пишите мейнтейнеру приватно.
Опишите:

- шаги воспроизведения;
- ожидаемое и фактическое поведение;
- версию (`python -c "import mini_llm_ui; print(mini_llm_ui.__version__)"`);
- окружение (ОС, Python, браузер).

Постарайтесь не публиковать рабочий эксплойт в issue, если уязвимость
позволяет выполнить произвольный код или украсть данные — сначала
дайте время на фикс.
